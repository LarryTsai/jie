## 一、分層原則

### 1. 頂層分區

| 區 | 定義 | 誰可以寫 | 不能放進來的東西 | 乾淨度 |
|---|---|---|---|---|
| **根目錄** | `README.md`（短首頁）、`ROADMAP.md`（分區地圖）、`AGENTS.md` | 主 Agent | 故事稿、母稿、公告流水 | 嚴格：只放這三檔 |
| **規則/** | 專案工作規則：競稿規約、正文凍結、Reviewer 協作、點火流程 | 作者裁定後由主 Agent 改 | 故事內容、寫作技法（技法放設定/00） | 嚴格：一條規則一檔，只放現行版 |
| **設定/** | Canon 查閱：世界、歷史、人物、修行、主線真相、寫作規則 | 主 Agent 同步；寫手只交方案 | 故事順序與篇章大綱、提案原稿、審查紀錄、工作流水 | 嚴格：每個事實只有一個現行出處，候選要標狀態 |
| **大綱/** | 故事：全書總覽 → 人生階段 → 篇／卷 → 篇章大綱與章綱 | 主 Agent 統整；寫手寫自己的競稿檔（在工作區） | 審查紀錄、已撤或已取代的舊稿、規約、討論會紀錄 | 嚴格：每列故事只有一個現行來源，就是總覽指的那份 |
| **待定與決策/** | 決策紀錄（D 號）、待定問題、候選提案 | 主 Agent；作者裁定後記錄 | 已定設定的正文、故事稿 | 中：可以有候選，但每檔要標狀態 |
| **工作區/** | 進行中的競稿、統一、盤點 | 寫手、Reviewer、PM，各寫各的檔 | 結案後的成果（收回主題資料夾或歸檔） | **允許散亂**；每個子資料夾要有日期、負責 session、結案條件 |
| **作者投放區/** | 作者放想法與草稿 | 只有作者寫；AI 只讀 | AI 產出 | 作者自己管（依該區 README） |
| **審查/** | Reviewer 報告、結構審查、驗證紀錄 | Reviewer、主 Agent | 故事正文與設定正文 | 中：按日期或主題分夾，不改舊報告結論 |
| **歸檔/** | 已取代、已撤、原始來源、舊卷號底稿、工作流水 | 主 Agent 只搬入；不改敘述，只修路徑 | 現行唯一版本 | 中：每個子夾 README 說明為何存放；不能從歸檔恢復撤用設定 |

### 2. 現行唯一版本，以及工作稿和歷史稿

- **現行唯一版本**只放設定/與大綱/。大綱以總覽的「唯一大綱來源」欄為準；設定以各分類 README 列出的專檔為準。
- **工作稿**（競稿、提案、盤點、統一任務）放工作區/或待定與決策/提案/。結案後，成果併入主題資料夾，過程稿移到歸檔，或在主題資料夾下的「來源／」子夾保留。
- **歷史**放歸檔/。舊卷號、88 歲年表、撤用篇、已吸收的討論會紀錄都屬此類。檔名不改，路徑改到歸檔後由 README 索引。
- **命名**：不用「本輪」「新卷」「Phase2」「新想法」這類時間相對詞做資料夾名或現行檔名。卷用兩位數 `卷07_東溟行`，篇用 `第15篇_九界金丹`，分段用 `段四_…`。

### 大綱階層說明

- **主軸**：用總覽的八個人生階段做第一層，第二層才是卷／篇。原因有三：總覽是唯一管理表，資料夾和它的節名一一對應，作者看總覽就知道檔在哪裡；「部」的編號在總稿 v3、年表與新弧之間還不一致（例如第一部包含首訪聖土）；卷號只覆蓋前十九卷，後段用篇號或段號。
- **檔或夾**：沿用設定結構審查的準則，單檔不開夾。卷二到卷十九都是一到二十KB 的單檔，直接放在階段夾下。開成資料夾的只有多檔篇和要拆的大檔：卷01、第07、08、15、17、18-19、20篇。
- **Phase2_後半部開荒改名的代價**：91 檔要分散到 00、03–06 和審查、歸檔、規則、工作區。全庫約 430 份 Markdown 的連結需要重算，其中總裁決檔有 43 條入鏈，年表有 77 條。好處是工作階段名不再當結構，九界大比之後的現行來源和舊稿、審查分開。這一步不可逆成本高，所以列為作者第一題。

   - 作者：總覽（缺口、衝突）→ 待定與決策/README 待裁題 → 工作區進行中清單

5. 維護規則
   a. 總覽同步：每份新大綱或作者裁定，同一輪改總覽對應列與檔頭統計

   h. 提交：逐檔 git add，多 session 先核 status
6. 變更紀錄：只記結構變動（日期｜變動｜對照表連結）
